# PatchCredit 预实验可行性研究框架
## 最新轻量化版本：数据集、代码实施、单 Baseline、Gate、产出物

> 版本：2026-08-19  
> 核心目的：**用最低实验成本判断 PatchCredit 是否值得继续做正式研究。**  
> 预实验主数据：**真实 LLM Compiler Agent 生成的多动作优化 Plan**。  
> 预实验原则：**不提前做正式论文级的大量 Baseline。**

---

# 0. 预实验到底要回答什么

预实验不负责证明：

> PatchCredit 已经优于所有现有方法。

预实验只回答三个问题：

```text
Q1. LLM Plan 里面到底有没有“可继续优化的空间”？
Q2. 最简单的 LOO 是否已经足够？
Q3. PatchCredit 能不能把这种空间转化成真实 Runtime 提升？
```

因此预实验的核心对象只有四个：

```text
1. LLM Plan
   研究起点，不是 Baseline

2. LOO
   预实验唯一真正的简单 Baseline

3. PatchCredit
   我们的方法

4. Exact Oracle
   小规模 Ground Truth / 理论上限，不是 Baseline
```

`-O3` 仍然要测，但它只负责：

```text
确认最初 LLM Plan 确实是有效优化
```

不作为 PatchCredit Pilot 的主方法对比项。

# 1. 预实验数据是什么

一个真正可用于 PatchCredit 的样本必须包含：

```json
{
  "plan_id": "task_x_attempt_03",
  "dataset": "cbench-v1",
  "task_id": "task_x",
  "model_id": "MODEL_NAME",
  "baseline_o3_runtime_ms": 100.0,
  "llm_plan": [
    "instcombine",
    "simplifycfg",
    "loop-unroll",
    "gvn",
    "licm"
  ],
  "compile_status": "PASS",
  "correctness_status": "PASS",
  "llm_runtime_ms": 84.0,
  "runtime_ci95": [83.3, 84.8],
  "action_count": 5
}
```

注意：

> Benchmark 本身不是 PatchCredit 的最终输入。

真正数据链是：

```text
Benchmark
→ LLM Compiler Agent
→ Optimization Plan
→ Build
→ Correctness
→ Repeated Runtime
→ Filter
→ PatchCredit Pilot Dataset
```

# 3.1 预实验模型配置冻结

预实验默认模型：

```text
Qwen2.5-Coder-3B-Instruct
```

部署位置：

```text
RTX 4090 24GB 本地推理
```

预实验禁止在不同 task 之间随意更换模型。

推荐配置文件：

```yaml
model:
  name: "Qwen2.5-Coder-3B-Instruct"
  deployment: "local"
  role: "compiler_plan_generator"
  temperature: 0.2
  max_output_tokens: 1024
  structured_output: true
```

其中 temperature / max_output_tokens 可在 P3 smoke test 后冻结一次，但冻结后不要因结果好坏频繁调整。

模型只负责：

```text
生成 4–8 action LLVM optimization plan
```

模型不负责：

```text
判断 Runtime
判断 Credit
判断 Interaction
决定 Oracle
```

这些必须由编译器和 PatchCredit 实验模块完成。

# P5：Exact Oracle
## 第一生死 Gate：LLM Plan 里面到底有没有可优化空间？

这是预实验最重要阶段之一。

对于每个 4–8 action Plan：

```text
穷举全部 order-preserving deletion subsets
```

数量：

```text
4 actions → 16
5 actions → 32
6 actions → 64
7 actions → 128
8 actions → 256
```

## 代码

`exhaustive.py`

```python
def enumerate_masks(n): ...
def apply_mask(plan, mask): ...
def evaluate_all_subsets(task, plan): ...
```

`oracle.py`

```python
def best_feasible_subset(records): ...
def full_plan_rank(records): ...
def negative_actions(records): ...
def redundant_actions(records): ...
def interactions(records): ...
```

## 先比较

这一阶段核心只有：

```text
LLM Plan
vs
Exact Oracle
```

例如：

```text
LLM Plan = 84 ms
Oracle   = 75 ms
```

说明：

```text
存在 9 ms 的可恢复优化空间
```

如果大量任务：

```text
LLM Plan ≈ Oracle
```

则 PatchCredit 没必要继续。

## 需要观察

- Negative Action；
- Redundant Action；
- Non-additive Interaction；
- Better Subplan；
- Full Plan Rank。

## Gate P5

GO 倾向：

```text
至少多个 Plan 存在稳定 better subplan
interaction 不是孤例
negative/redundant action 不是孤例
effect 大于 noise
```

建议参考线：

```text
>= 30% Plan 有稳定 Interaction
>= 20% Plan 有更优合法 Subplan 或明显 Pareto 改善
```

这些是预实验工程 Gate，不是已有实验事实。

## 产出

# P7：低预算选择 + 在线 Recomposition
## 第三 Gate：第二创新和最终性能能不能一起成立？

为了避免 Pilot 过重，这一阶段**不再引入 Random / Shapley 等额外 Baseline**。

只回答：

> 在不读取完整 Oracle 的条件下，PatchCredit 能不能用有限测量次数找到一个优于 LLM、最好也优于 LOO 的 Plan？

---

## 预算定义

例如：

```text
B = min(20, 3 * action_count)
```

或：

```text
B = 10 / 20 / 30
```

具体在 P5 后冻结。

## PatchCredit 选择策略

优先：

```text
高不确定性
高 decision impact
疑似 strong interaction
疑似 negative action
```

## 代码

`budgeted_selector.py`

```python
def propose_next(history, plan, budget_left): ...
```

`recompose.py`

```python
def propose_repair(plan, credit, interactions): ...
def clean_verify(task, candidate): ...
```

---

## 最终只比较

```text
LLM Plan
LOO Repair
PatchCredit Repair
Oracle
```

其中：

```text
Oracle
```

只用于评价“离 Ground Truth 多远”，PatchCredit 算法本身不能读取 Oracle。

## 核心指标

### 1. PatchCredit 对 LLM 的额外提升

```text
ExtraSpeedup =
Runtime(LLM) / Runtime(PatchCredit) - 1
```

### 2. PatchCredit 对 LOO 的额外提升

```text
PC_vs_LOO =
Runtime(LOO) / Runtime(PatchCredit) - 1
```

### 3. Oracle Gain Recovery

若：

```text
LLM = 84
Oracle = 75
PatchCredit = 76
```

则：

```text
Recoverable Gain = 84 - 75 = 9
Recovered Gain   = 84 - 76 = 8
Gain Recovery Rate = 8 / 9 = 88.9%
```

### 4. Measurement Budget

记录：

```text
真实编译/运行了多少个 intervention
```

第二创新的预实验目标不是证明“全面击败所有采样算法”，而是先证明：

> **PatchCredit 不需要穷举，也能在有限预算下接近 Oracle。**

与 Random/Shapley 的正式同预算比较放到正式实验。

# P8：最终 GO / CONDITIONAL GO / NO-GO

## GO

同时大体满足：

```text
A. >= 8 个真实成功 LLM Plans
B. Runtime measurement 稳定
C. LLM Plan 与 Oracle 存在明显差距
D. Negative / Redundant / Interaction 是重复现象
E. PatchCredit 比 LOO 有额外价值
F. PatchCredit 在有限 budget 下能接近 Oracle
G. clean rerun 有真实 Runtime gain
```

---

## CONDITIONAL GO

### 情况 1

```text
PatchCredit 比 LLM 好
但和 LOO 差不多
```

说明：

> 二次优化有价值，但复杂 Contextual Credit 可能没必要。

此时不直接进入当前三创新版本。

### 情况 2

```text
PatchCredit 比 LOO 好
但有限 budget 下效果不稳定
```

说明：

> 主创新可继续，但 Budgeted Sampling 暂时不能当正式独立创新。

### 情况 3

```text
PatchCredit 接近 Oracle
但额外 Runtime 提升很小
```

需要重新判断是否转向：

```text
Plan diagnosis / compactness / explanation
```

---

## NO-GO

任意严重情况：

```text
真实成功 LLM Plans 几乎拿不到
Runtime noise 不可控
LLM Plan 基本就是 Oracle
LOO 已经完全够用
PatchCredit 无法稳定进一步提高 Runtime
```

---

```text

```
