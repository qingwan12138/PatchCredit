# 0. 先回答：预实验到底需要什么数据

一个真正可用于 PatchCredit 的预实验样本必须长这样：

```json
{
  "plan_id": "cbench_qsort_attempt_03",
  "dataset": "cbench-v1",
  "task_id": "qsort",
  "model_id": "MODEL_NAME",
  "baseline": {
    "pipeline": "-O3",
    "runtime_median_ms": 100.0
  },
  "llm_plan": [
    "instcombine",
    "simplifycfg",
    "loop-unroll",
    "gvn",
    "licm"
  ],
  "compile_status": "PASS",
  "correctness_status": "PASS",
  "runtime_median_ms": 83.0,
  "runtime_ci95": [82.4, 83.7],
  "speedup_vs_baseline": 0.2048,
  "action_count": 5
}
```

注意：

> **Benchmark 本身不是这个样本。**

Benchmark 只提供程序。

真正样本需要自己经过：

```text
Benchmark
→ LLM Plan Generation
→ Compiler
→ Correctness
→ Runtime
→ Filtering
```

# 1. 有哪些现成 benchmark 可直接起步

# 1.1 主候选：CompilerGym cbench-v1

官方 CompilerGym LLVM 文档：

```text
benchmark://cbench-v1
Num. Benchmarks = 23
Description = Runnable C benchmarks
Validatable = Partially
```

因此它非常适合做第一候选池，但不能把 23 个全部默认当作合格实验样本。

官方还说明：

```text
Runtime observation:
compile and run benchmark
returns a list of wall-clock execution times
```

但 Runtime API 被标为：

```text
Experimental API
```

因此预实验政策：

```text
CompilerGym 提供 benchmark/action/runtime 基础设施
+
我们自己做严格筛选、raw sample 保存和 correctness 审计
```

来源：
- https://compilergym.com/llvm/index.html

---

# 1.2 第二候选：PolyBench/C

官方 PolyBench/C：

```text
30 numerical computations
static control parts
designed to uniformize execution and monitoring
```

特别适合：

- 稳定 runtime；
- 小 kernel；
- 4–8 action subset exhaustive evaluation；
- 第二独立数据源复验。

来源：
- https://www.cs.colostate.edu/~pouchet/software/polybench/

---

# 1.3 正式扩展：LLVM test-suite

LLVM 官方说明：

- test/benchmark programs；
- reference outputs；
- runtime；
- compilation time；
- code size。

预实验不建议一开始全部接入，因为工程量大。

来源：
- https://llvm.org/docs/TestSuiteGuide.html

---

# 1.4 Compiler-R1 能提供什么

Compiler-R1 可以提供：

```text
LLM compiler agent workflow
pass sequence generation ideas
public code/data
```

但其公开主目标主要是：

```text
LLVM IR instruction count reduction
```

所以它适合作为：

```text
Agent scaffold / Plan generator reference
```

不适合作为：

```text
PatchCredit Runtime Ground Truth
```

必须重新跑 runtime。

来源：
- https://github.com/Mind4Compiler/Compiler-R1

# 2. 预实验最终数据集设计

建议最终形成两个集合。

## Set A：PatchCredit-cBench-Pilot

目标：

```text
8–12 个 accepted LLM Plans
来自 6–10 个 cBench tasks
每个 Plan 4–8 actions
```

## Set B：PatchCredit-PolyBench-Pilot

目标：

```text
4–8 个 accepted LLM Plans
来自不同 PolyBench kernels
每个 Plan 4–8 actions
```

为什么两个集合：

- cBench 更接近 runnable application benchmarks；
- PolyBench 更适合稳定性能测量；
- 如果现象只在一个 suite 出现，风险较高。

# P5：Exact Oracle —— 核心生死阶段

## 目标

对每个 4–8 action accepted Plan：

```text
穷举所有 order-preserving deletion subsets
```

例如 6 actions：

```text
64 subsets
```

8 actions：

```text
256 subsets
```

## 为什么先只做 deletion

这样可以控制变量：

- 不引入 reorder 的新 IR 轨迹复杂性；
- 可以建立精确 Oracle；
- 先判断核心现象是否真实存在。

## 代码

`exhaustive.py`

```python
def masks(n):
    return range(1 << n)

def apply_mask(plan, mask):
    ...

def evaluate_all_subsets(task, plan):
    ...
```

## 每 subset 记录

```text
plan_id
mask
actions
build_status
correctness
runtime samples
median
CI
utility
```

## 需要回答

### Q1 Negative action
删除后更快吗？

### Q2 Redundant action
删除后在 noise margin 内几乎不变吗？

### Q3 Interaction
两个 action 的组合效应不是简单相加吗？

### Q4 Better subplan
是否存在子计划真实快于完整 LLM Plan？

### Q5 Full-plan rank
完整 LLM Plan 在所有 feasible subsets 里排第几？

## Gate P5

建议 GO 信号：

```text
>= 30% plans 有稳定 non-additive interaction
>= 20% plans 有更优合法 subplan 或明显 Pareto 改善
negative / redundant actions 不只是一个孤例
effects > noise
```

这些是预实验工程 Gate，不是已有事实。

## NO-GO

如果：

```text
绝大部分 full LLM Plan 已经是最优
+
interaction 很少
+
negative/redundant 几乎没有
```

立即停止。

## 产出

```text
outputs/p5/oracle/*.parquet
outputs/p5/oracle_summary.csv
outputs/p5/full_plan_rank.csv
outputs/p5/negative_actions.csv
outputs/p5/interactions.csv
outputs/p5/P5_PHENOMENON_REPORT.md
```

# P9：最终 Go / Conditional Go / No-Go

## GO

至少：

```text
A. >= 8 accepted real LLM Plans
B. Runtime measurement reliable
C. Interaction / negative / redundancy 是重复现象
D. Full LLM Plan 并非总最优
E. PatchCredit 不被 LOO 完全替代
F. Budgeted sampler 有证据
G. Recomposition 有真实 Runtime gain
```

## CONDITIONAL GO

例 1：

```text
Credit 有价值
Recomposition 有价值
但 Sampling 不优于 baseline
```

则论文改为：

```text
主创新：Contextual Credit
支撑：Recomposition
支撑：Runtime-proxy disagreement / robustness
```

例 2：

```text
Sampling 有价值
但 extra speedup 很小
```

可能转成：

> low-budget diagnosis / compact plan

## NO-GO

```text
LLM Plan 数据拿不到
Runtime 不稳定
核心 interaction 不存在
LOO 完全够用
Recomposition 没收益
```

## 最终产出


# 4. 预实验预计数据规模

这是工程规划，不是结果。

## Raw generation

```text
cBench:
10-15 tasks × 3-5 attempts
= 30-75 raw plans

PolyBench:
8-10 kernels × 2-3 attempts
= 16-30 raw plans
```

总：

```text

```

希望最终筛出：

```text

```

如果 accepted rate 很低，不要盲目把 LLM API 数量加到几千次，先检查：

- Prompt 是否合理；
- allowed passes 是否太窄/太宽；
- runtime goal 是否太难；
- baseline 是否设置过强；
- plan length 是否不合理。

# 6. 预实验最重要的三道 Gate

如果只记三个：

## Gate 1：P4
有没有足够的 **真实成功 LLM Plans**？

## Gate 2：P5
这些 Plans 里有没有 **真实 Credit / Interaction / better subplan 现象**？

## Gate 3：P6-P8
这些现象是不是 **LOO 解决不了，而且 PatchCredit 能转换成 Runtime gain**？

三个 Gate 全过：

> 才值得做正式研究。
