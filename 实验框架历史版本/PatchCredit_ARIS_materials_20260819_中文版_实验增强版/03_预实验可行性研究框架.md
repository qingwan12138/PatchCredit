# PatchCredit 预实验可行性研究框架（Go / No-Go 版）

> 版本：2026-08-19  
> 定位：不是为了“把论文结果先跑一遍”，而是以最低工程和计算成本判断 PatchCredit 的核心研究假设是否真实存在。  
> 结论要求：预实验结束后必须明确给出 **GO / CONDITIONAL GO / NO-GO**，禁止因为已经写了代码而默认继续。

---

# 1. 预实验只验证四件事

### F1：多编辑性能 Patch 里是否真的有“可归因现象”？
是否存在负贡献编辑、冗余编辑、协同、冲突？

### F2：完整 Patch 是否经常不是最优组合？
如果所有完整 Patch 都已经接近组合最优，PatchCredit 没有足够重组空间。

### F3：有限采样是否有机会替代穷举？
如果 random/LOO 用极少测量就已经找到最优组合，复杂 sampler 没有研究必要。

### F4：这一现象在 LLM Patch 上是否至少初步存在？
专家 Patch 上成立只能证明“性能编辑有 interaction”，还不能证明 PatchCredit 的 LLM 研究定位成立。

---

# 2. 预实验总体路线

```text
P0 环境与测量器 smoke test
        ↓ Gate 0
P1 GSO 候选任务扫描
        ↓ Gate 1
P2 专家 Patch 拆成 3–6 个编辑单元
        ↓ Gate 2
P3 穷举合法子集，建立真实性能 Oracle
        ↓ Gate 3：核心现象是否存在？
P4 离线预算采样对比
        ↓ Gate 4：复杂 sampler 是否有必要？
P5 最简 PatchCredit 模型 + 重组
        ↓ Gate 5：能否找回近最优组合？
P6 小规模 LLM Patch 复验
        ↓ Gate 6：LLM 场景是否成立？
P7 Go / No-Go 决策
```

**预实验阶段不要实现正式版全部功能。** 不做复杂 UI、不做训练、不做大规模 agent 平台、不做多 benchmark 全量跑。

# Phase P0：环境与测量器 Smoke Test

## 目标
先证明你能稳定测到同一个程序的 runtime，而不是先写 attribution 算法。

## 输入

- 本机/服务器环境；
- 1 个 GSO 可运行任务；
- benchmark baseline；
- reference patch。

## 代码任务

### P0.1 `benchmark_gso.py`
只实现四个函数：

```python
prepare_task(task_id, dst) -> Path
run_correctness(workspace) -> bool
run_perf_once(workspace) -> float
apply_patch(workspace, patch_text) -> None
```

### P0.2 `runtime_measure.py`

```python
def measure(workspace, warmup=3, repeat=15) -> dict:
    # 返回 raw_times / median / std / cv / bootstrap_ci
```

必须保留 raw times。

### P0.3 `p0_smoke.py`
连续执行：

1. baseline 15 次；
2. full reference patch 15 次；
3. baseline 再 15 次。

测试是否出现明显温漂/后台噪声。

## Gate 0

**通过：**

- correctness 可自动执行；
- baseline 两个 session 的中位数差异不大于预设 noise floor；
- full patch 与 baseline 的差异可重复观察。

**不通过：**先修测量环境，禁止进入 P1。

## 产出清单

- `outputs/p0/environment.json`
- `outputs/p0/raw_timings.jsonl`
- `outputs/p0/noise_summary.csv`
- `outputs/p0/P0_GATE.md`

# Phase P1：GSO 候选任务筛选

## 为什么第一轮用 GSO
GSO 是现成的真实软件性能优化 benchmark，包含 102 个任务和自动性能测试。预实验不需要 102 个全跑，只需要找到一小批适合“多编辑归因”的稳定任务。

## 目标
从候选中找到 **10–15 个真正适合 PatchCredit 的 expert patch**。

## 代码任务

### `p1_screen.py`
对候选任务逐个生成：

```python
{
  "task_id": ..., 
  "baseline_correct": true,
  "patch_correct": true,
  "baseline_median_ms": ...,
  "patch_median_ms": ...,
  "speedup": ...,
  "noise_cv": ...,
  "files_changed": ...,
  "hunks": ...,
  "rough_edit_groups": ...,
  "accepted": true,
  "reason": ...
}
```

### 预筛条件

- reference patch 通过 correctness；
- speedup 稳定可测；
- 至少 3 个逻辑修改；
- 最理想 3–6 个 unit；
- 单次性能测试不能贵到无法做几十个子集；
- 暂时优先容易复现的任务，不追求语言覆盖。

## Gate 1

**GO：**至少找到 10 个稳定的 3–6 unit 候选。  
**CONDITIONAL：**找到 5–9 个，允许继续 P2/P3，但必须继续补任务。  
**NO-GO：**少于 5 个，说明数据层本身就不适合当前框架，先解决任务来源。

## 产出清单

- `outputs/p1/screening.csv`
- `outputs/p1/accepted_tasks.jsonl`
- `outputs/p1/rejected_tasks.csv`
- `outputs/p1/P1_GATE.md`

# Phase P2：编辑单元拆分与合法组合生成

## 目标
证明“完整 Patch 可以被拆成多个真正可组合的编辑单元”。

## 预实验阶段不要过度工程化
第一版采用：**Git hunk + AST/同一符号规则 + 人工复核**。不要马上实现完整 LLM unitizer。

## 代码任务

### `diff_units.py`

```python
parse_diff(patch_text) -> list[Hunk]
group_hunks(hunks, source_tree) -> list[EditUnit]
manual_override(units, override_yaml) -> list[EditUnit]
apply_units(base_repo, units, selected_ids) -> ApplyResult
```

每个 task 允许一个人工审核文件：

```yaml
merge:
  - [u1, u2]
depends_on:
  u4: [u3]
notes:
  u5: "helper function must exist before call-site edit"
```

### 最低测试

对每个 task：

- full unit set 重构后的 diff 必须与原 patch 语义等价；
- 空集合 = baseline；
- 每个单 unit 或 dependency closure 至少尝试 build/test；
- 保存哪些子集因为 dependency 无法合法构造。

## Gate 2

每个入选 task 至少应满足：

- `3 <= n_units <= 6`；
- 除 full patch 外还有多个 correctness-pass 子集；
- 不是所有 unit 都被一条依赖链绑定成“只能全选”。

如果多数 Patch 最终只有 1–2 个不可分单元，这是核心 **Kill Condition**。

## 产出清单

- `outputs/p2/<task>/units.json`
- `outputs/p2/<task>/dependencies.json`
- `outputs/p2/<task>/manual_override.yaml`
- `outputs/p2/<task>/subset_feasibility.csv`
- `outputs/p2/P2_GATE.md`

# Phase P3：穷举子集，建立性能 Oracle

## 这是整个预实验最关键阶段
现在先不研究“怎么聪明地采样”，直接把小 Patch 的组合尽量全部跑完，回答：**PatchCredit 想研究的现象到底存不存在？**

## 规模

- 先选 P2 中最干净的 **5–10 个 task**；
- 每个 3–6 unit；
- 6 unit 最多 64 个原始组合，dependency closure 后通常更少；
- 每个正确子集做 warmup + repeated timing。

## 代码任务

### `subset_runner.py`

```python
enumerate_subsets(units, deps) -> list[Subset]
run_subset(task, subset) -> SubsetResult
```

`SubsetResult` 必须区分：

- `APPLY_FAIL`
- `BUILD_FAIL`
- `TEST_FAIL`
- `PASS_MEASURED`

### `oracle_analysis.py`
性能 utility：

\[
v(S)=\log(T_{base}/T(S))
\]

计算：

1. full patch speedup；
2. best subset speedup；
3. 每个 unit 的 LOO effect；
4. 单 unit effect；
5. pairwise interaction；
6. 是否存在负贡献 unit；
7. 是否存在“删掉某 unit 后更快”；
8. speedup–patch-size Pareto frontier。

pairwise interaction 最简定义：

\[
I_{ij}(S)=v(S+i+j)-v(S+i)-v(S+j)+v(S)
\]

显著 interaction 不只看数值大小，还必须大于测量 noise floor。

## Gate 3：现象 Gate

建议把以下阈值预注册为“继续研究的参考线”，不是论文最终结果：

### 强 GO

- ≥30% 的 Patch 至少存在一组**超过 noise floor 的非加性交互**；
- ≥20% 的 Patch 存在正确子集，其 runtime **显著优于 full patch**，或出现明显的 speedup/编辑数 Pareto 改善；
- 至少观察到若干负贡献/冗余 unit；
- 同一重要 interaction 在重复 session 中方向基本稳定。

### CONDITIONAL GO
interaction 明显，但 full patch 通常已经最优。此时研究可转成“解释 + 预算化归因”，但“进一步性能提升”主张应降级。

### NO-GO

- interaction 极少或都小于测量噪声；
- full patch 几乎总是最优；
- 大多数子集 correctness fail，无法形成有意义 coalition；
- credit 排名跨 session 完全不稳定。

## 产出清单

- `outputs/p3/<task>/all_subsets.csv`
- `outputs/p3/<task>/raw_measurements.jsonl`
- `outputs/p3/<task>/interaction_matrix.csv`
- `outputs/p3/<task>/pareto.csv`
- `outputs/p3/oracle_summary.csv`
- `outputs/p3/P3_PHENOMENON_REPORT.md`

**如果 P3 是 NO-GO，建议直接停止 PatchCredit，不进入 P4。**

# Phase P4：离线预算采样必要性测试

## 目标
不用再执行程序，直接利用 P3 已有 Oracle table 模拟：如果我们只看到一部分子集，能否比 random/LOO 更快找到好组合？

## 为什么这样做
这是最低成本判断“Budgeted Interaction Sampling 是否值得成为支撑创新”的办法。

## 代码任务

### `sampler_baselines.py`
实现：

```python
random_sampling(table, budget, seed)
loo_first(table, budget)
ddmin_like(table, budget)
greedy_single_effect(table, budget)
```

### `patchcredit_lite.py`
第一版不要复杂：

1. 初始测 empty/full/singletons/少量 pairs；
2. 拟合带 pairwise term 的 sparse regression；
3. 根据 prediction uncertainty + potential interaction 选下一个 subset；
4. 每次只暴露 Oracle table 中对应观测，模拟真实在线过程。

### 预算

对每个 task 测：

- 20% legal subsets；
- 30%；
- 50%；

每种 stochastic 方法至少多个 seed。

## 指标

- best-found speedup / oracle-best speedup；
- regret；
- 是否找到 oracle top-5% candidate；
- 找到 95% oracle-best utility 所需测量数。

## Gate 4

### GO
PatchCredit-lite 在 ≤50% legal-subset 预算下，在多数 task 上比 random/LOO/ddmin 更稳定地恢复近最优 candidate。

### NO-GO / 降级
若 LOO/ddmin 几乎总能用更少测试找到相同 candidate，则“复杂 budgeted sampler”不值得作为独立创新，应降级成工程组件。

## 产出清单

- `outputs/p4/budget_results.csv`
- `outputs/p4/regret_curves.csv`
- `outputs/p4/per_seed_results.jsonl`
- `outputs/p4/P4_SAMPLER_GATE.md`

# Phase P5：PatchCredit-Lite 在线重组测试

## 目标
从“离线 replay”走到真正在线：算法自己选择 subset → 真编译 → 真测试 → 真测 runtime → 更新模型。

## 规模

只选 P3 中 **3–5 个代表 task**：

- 1 个协同强；
- 1 个存在负贡献；
- 1 个 full patch 已较优；
- 可再加 1–2 个中等难度。

## 代码任务

`patchcredit_lite.py` 暴露：

```python
state = init(task, budget)
while state.remaining_budget > 0:
    subset = propose(state)
    obs = runner.evaluate(subset)
    state = update(state, obs)
final_candidates = recommend(state, top_k=5)
```

最后 top-k 必须全部重新测量，不能直接拿模型 prediction 当最终结果。

## Gate 5

- 能在固定预算内找到接近 Oracle best 的正确子集；
- 最终选择不是偶然单次快，需要独立 re-measure；
- 至少部分 task 能达到 full patch 以上性能，或明显 Pareto 改善。

## 产出清单

- `outputs/p5/online_trace/*.jsonl`
- `outputs/p5/recommended_patches/*.diff`
- `outputs/p5/revalidation.csv`
- `outputs/p5/P5_ONLINE_GATE.md`

# Phase P6：小规模 LLM Patch 复验

## 目标
验证核心现象不是“只存在于人类专家 Patch”。

## 重要原则
这一步放到最后，是为了避免在研究假设还没成立时浪费大量模型额度。

## 实验规模建议

从已稳定的 GSO task 中选 5–10 个，让 1–2 种固定 LLM/agent 各尝试若干次性能优化。**不要求每个 attempt 成功**；只收录：

- correctness pass；
- runtime 明显优于 baseline；
- 3 个以上编辑单元。

目标不是凑成功率，而是获得一个小型 **successful multi-edit LLM patch** 集合。

## 代码任务

### `llm_patch_collector.py`

```python
generate(task, model_config) -> Attempt
validate(attempt) -> ValidatedAttempt
accept(validated) -> bool
```

必须保存：

- prompt；
- model/version；
- attempt id；
- patch diff；
- correctness；
- raw timing；
- trajectory（若工具提供）。

对收集到的成功 Patch 重复 P2–P5，但只做小规模。

## Gate 6

### GO
能获得若干稳定的 successful multi-edit LLM patches，并在其中观察到与 expert patch 相同类型的负贡献/interaction/可重组空间。

### CONDITIONAL GO
LLM 成功 Patch 太少，但已有 Patch 中现象成立。正式实验可扩大生成预算或引入其他性能 benchmark/agent，但论文题目暂时不要把“LLM Patch”写得过强。

### NO-GO
有足量 LLM 成功 Patch，但几乎不存在 interaction/重组空间；这直接削弱 PatchCredit 的核心定位。

## 产出清单

- `outputs/p6/all_attempts.jsonl`
- `outputs/p6/accepted_llm_patches.jsonl`
- `outputs/p6/patches/*.diff`
- `outputs/p6/llm_oracle_summary.csv`
- `outputs/p6/P6_LLM_GATE.md`

  "llm_case_supported": true,
  "decision": "GO",
  "blocking_risks": [],

## 推荐决策矩阵

| 条件 | 决策 |
|---|---|
| P3 强、P4 强、P6 强 | **GO：按完整 PatchCredit 推进** |

# 4. 预实验最低代码实现顺序

如果交给 Codex/Claude Code，不要让它一次性把正式项目全写完。按以下顺序逐阶段提交：

1. **Task 01：GSO 单任务 checkout/build/test/perf**

**每个 Task 必须同时提交：实现代码、至少一个测试、CLI/脚本、示例输出；上一 Task 的 Gate 不通过，不开始下一 Task。**

# 6. 预实验真正应该得到的结论

最理想的预实验不是先拿到一个很大的平均 speedup，而是得到下面这条证据链：

1. **真实多编辑性能 Patch 中确实存在可重复的正/负贡献与非加性交互；**
2. **完整 Patch 在一部分任务上不是性能最优组合；**
3. **小规模穷举能给出 ground truth；**
4. **有限预算方法比简单删除/随机搜索更容易恢复近最优组合；**
5. **至少在一小批 successful LLM patches 上同样观察到这种现象。**

如果五条都成立，再进入正式实验是合理的；如果第 1 或第 5 条失败，就应该及时停止或改题，而不是继续堆系统工程。
